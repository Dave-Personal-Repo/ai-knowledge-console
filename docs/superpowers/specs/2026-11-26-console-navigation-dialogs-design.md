# Console navigation, dialogs and role permissions — short design

## Intent

The operator wants the console to behave like a workspace rather than a sequence of page replacements:

- Each command in **Hub operations** opens in a popup, as member details now do.
- Opening a document from **Knowledge** or **Rules & policies** splits the view: the filtered list stays visible on the left and the document opens on the right. This applies to both menus.
- The originating menu stays highlighted while a document is open. Today every document route highlights **Knowledge**, including policies.
- Each visible role card can show the role's full permission list. A `CODE_OWNER` must see only `CODE_OWNER` and lower roles; `SUPER_OWNER` and its permissions must be absent from both the cards and any dialog.

## Goals

- Reuse the native-`<dialog>` pattern already approved for member details; no new frontend dependency.
- Keep the server-side role filter, fixed command allowlist and `confirm: true` mutation gate authoritative.
- Keep filters, sorting and the selected document usable together in the split view.
- Make direct links to documents highlight the correct menu without depending on click history.

## Non-goals / anti-goals

- No new `kb` commands, no arbitrary runner, no change to how permissions are enforced.
- No change to Docker mounts or mutation semantics; changing commands still need `npm start` against a writable clone.
- No new sign-in or per-user identity; the single hub identity from `kb whoami` remains.
- No visual theme redesign beyond the layout needed for split panes and dialogs.

## Constraints

- Routes are hash-based: `#/library`, `#/policies`, `#/doc/<source:path>`. `parseRoute()` returns `doc` for every document, and `markNav()` currently hardcodes `doc` → `library` (`public/app.js:140-144`). That is the active-menu bug.
- `renderDoc()` currently replaces `view.innerHTML` with a reader layout (`public/app.js:425-464`), which is why the list disappears.
- Document items carry `kind` (`knowledge`, `policy`, `guide`) and `id` (`source:path`) from `/api/inventory`. `item.kind` is enough to choose the correct menu for both clicked and directly linked documents.
- `filterInventoryForRole()` already removes roles above the session from `roleScopes`, `permissionCounts` and `members` (`server.js:78-87`). The UI must consume only that filtered inventory; it must never read the raw hub config.
- Command forms are generated by `commandForm()` and submitted via a `submit` listener on `view`. A dialog lives outside `view`, so it needs its own submit/change/close listeners, as the member dialog already does.

## Approaches

1. **Reusable dialogs + cached split reader (chosen).** One command dialog, one role-permission dialog, and a small cache of the currently rendered document. The list pane re-renders on filter changes while the reader pane reuses the cached document. This reuses existing helpers, avoids refetching, and keeps direct links correct by deriving the menu from `item.kind`.
2. **One dialog per command rendered into the operations page.** Simpler HTML but duplicates close/submit wiring many times and leaves stale results behind; rejected as harder to keep consistent.
3. **Store the origin menu in the URL for documents.** Works for clicked documents but direct links have no origin; deriving from `item.kind` is simpler and correct in both cases. Rejected.
4. **Replace the whole view with two panes but discard filters when reading.** Smallest change, but the operator explicitly wants to keep browsing; rejected.

## Implementation outline

- Add a generic `openDialog(dialog, body)` / `closeDialog(dialog)` helper pair and reuse it for member, command and role dialogs. Keep `showMemberDialog`/`closeMemberDialog` names for the live proof already in place.
- **Hub operations:** render compact command cards with an **Open** button; clicking it fills a `<dialog id="command-dialog">` with `commandForm(command)` and its own submit/close listeners. `confirm: true` and server validation remain unchanged.
- **Split reader:** add `state.openDoc` cache (`id`, document, rendered HTML). On document route, render a two-pane shell: left pane uses the existing list markup and filters for the inferred kind; right pane uses the cached reader. Clicking another card fetches and caches that document, then updates only the reader pane. Filter changes re-render the shell without refetching. Stack panes on narrow screens.
- **Active menu:** `markNav()` resolves a document's `item.kind`; `policy` highlights **Rules & policies**, everything else highlights **Knowledge**. Update the reader's back button to return to the inferred section.
- **Role permissions:** add `<dialog id="role-dialog">` and a **View permissions** button to each role card. The dialog lists permissions from `state.inventory.roleScopes[role]` only. Because a `CODE_OWNER` inventory excludes `SUPER_OWNER`, neither the card nor the dialog can expose that role.
- **Tests:** extend static UI tests for the new hooks; add server-side assertions that a `CODE_OWNER` inventory contains no `SUPER_OWNER` role or permission list; verify live after `make restart` with the existing CDP method (command popup, split panes, policy nav highlight, role dialog, no `SUPER_OWNER` data for a `CODE_OWNER` session).
